ARM CCA + KVM:
How Multiple Guest OSes Work with RME

The answer requires understanding one architectural decision ARM made that is genuinely elegant: KVM and RMM are two different hypervisors, running in two different security worlds, with a deliberate and principled split of authority between them.

The "Aha" Moments

1. Two Hypervisors, Two Jobs — A Principled Split of Authority

ARM's architecture specification explicitly documents the design principle (verified from official ARM documentation):

ARM CCA Design Principle — Verified from ARM Den0125 Policy: decisions about which resources to allocate to a Realm — CPU cycles, memory, devices. This is the responsibility of KVM in Normal EL2.

Mechanism: enacting policy decisions that change architectural state, when those changes cannot be trusted to the hypervisor. This is the responsibility of RMM in Realm EL2.

KVM remains the resource scheduler — it decides which physical pages a Realm gets, which pCPUs run which vCPUs, which devices are assigned. KVM retains full control plane authority. What KVM loses is data plane authority — once pages are delegated to the Realm, KVM cannot observe or modify what is in them.

Stated simply: KVM is the landlord who allocates rooms. RMM is the locksmith who changes the locks once a tenant moves in. The landlord cannot enter after the lock is changed — not by policy, but because the hardware key no longer works for them.

2. Memory Delegation Is One-Way — The Same Lock Pattern, Applied Per-Page

When KVM decides to give physical pages to a Realm VM, it calls RMI_GRANULE_DELEGATE via SMC. The CPU traps to EL3 (Root Monitor). The Root Monitor updates the GPT for those pages: GPI_NS → GPI_REALM. The Root Monitor then switches to RMM at Realm EL2 to complete the operation.

KVM (Normal EL2)
  │  SMC: RMI_GRANULE_DELEGATE(page_PA)
  ▼
Root Monitor (EL3)
  │  Updates GPT: page_PA → GPI_REALM
  │  Switches to Realm EL2
  ▼
RMM (Realm EL2)
  │  Receives delegation, assigns to Realm VM
  │  Updates RTTs (Realm Translation Tables)
  ▼
  Page is now Realm PAS
  Any Normal world access → GPC fault (hardware, immediate)
  KVM cannot read, write, or remap this page
The Lock Pattern — Recognised from the framework This is the same architectural pattern as SSC (Cortex-M55 SoC), HDP (STM32), and SMMU_s_CONF lock — a trusted entity at the highest privilege level updates a protection table, after which the untrusted entity (here: KVM) cannot access the protected resource. The difference: SSC/HDP lock is boot-time and per-region. GPT delegation is runtime and per-page. The principle is identical.

One important nuance verified from the Linux kernel patch series: KVM can destroy a Realm VM at any time, which forces undelgation of all its pages back to NS PAS. KVM retains lifecycle authority (create and destroy) — it loses memory-access authority during the lifetime of a running Realm.

3. The Realm VM Controls Its Own I/O Boundary

Because KVM cannot access Realm memory, standard virtio I/O (which relies on the hypervisor reading and writing guest buffers) cannot work directly. The solution inverts the traditional authority model in an elegant way:

The Realm VM itself decides which pages to make available for I/O. Using the RSI (Realm Services Interface) — a call from Realm EL1/EL0 up to RMM at Realm EL2 — the guest can transition specific pages from Realm PAS to NS PAS (GPI_NS), making them accessible to the hypervisor for device I/O.

Realm VM (R-EL1)
  │  RSI_IPA_STATE_SET(buffer_page, NS)
  ▼
RMM (R-EL2)
  │  SMC to Root Monitor
  ▼
Root Monitor (EL3)
  │  Updates GPT: buffer_page → GPI_NONSECURE
  ▼
  KVM can now DMA device ↔ buffer_page
  Realm VM retains control — it chose which page to share
  KVM cannot pull pages out; Realm pushes them out
Authority inversion In traditional virtualisation, the hypervisor decides what memory the guest can access. In CCA, the Realm VM decides what memory the hypervisor can access. The guest controls its own I/O boundary, not the hypervisor.

4. GPC: The Same Target-Side Pattern at 4KB Granularity

The Granule Protection Check (GPC) fires at the output of every MMU and SMMU translation — both stage 1 and stage 2, for both CPU and DMA. When any translation produces a physical address, the GPC looks up that PA in the GPT. If the accessing security world does not match the GPT entry, a Granule Protection Fault occurs.

This maps directly into the framework:

The "Aha" — Confidential Computing = Fine-Grained MPC GPT/GPC is not a new security pattern. It is the same target-side access control pattern as TZASC and MPC — applied at 4KB per-page granularity with four-world identity instead of binary Secure/NonSecure. Confidential computing extended the granularity, not the principle.

The Attestation Flow

The Realm VM's attestation is managed entirely within the trusted components — RMM and Root Monitor. KVM and the host OS are not in the attestation path at all.

Realm VM (R-EL1) requests attestation:
  RSI_ATTESTATION_TOKEN_INIT (nonce from relying party)
  RSI_ATTESTATION_TOKEN_CONTINUE
        │
        ▼
RMM (R-EL2) collects measurements:
  RIM  — Realm Initial Measurement (initial image digest)
  REM  — Realm Extensible Measurement (runtime measurements)
  RMM measurement itself (measured at boot by Root Monitor)
        │
        ▼
Root Monitor (EL3) signs the token:
  Platform private key (device certificate chain)
  Produces: CCA token (CBOR, per IETF RATS RFC 9334)
        │
        ▼
Token returned to Realm VM → forwarded to relying party

TCB components visible in attestation:
  • CPU hardware (RME extension)
  • Root Monitor (TF-A, measured at boot)
  • RMM (measured, in attestation token)
  • Realm VM initial image (RIM)

NOT in TCB:
  • KVM  ← removed from trust path entirely
  • Host Linux
  • Other Realm VMs
  • Other guest VMs in Normal world

The SGX ↔ NSC/SG parallel — from your 2022 article Your observation about SGX's ECALL gateway being structurally equivalent to ARM Cortex-M33's NSC/SG mechanism is precise. Both define hardware-enforced controlled entry points into a protected domain. Both cause a fault on arbitrary branches. The difference: SGX enforces at the CPU instruction level (EENTER must target a valid TCS); ARM NSC enforces at the branch target (must land on SG instruction). Same pattern, different implementation depth.

A Note on Memory Encryption

ARM CCA's hardware architecture specification states that isolation is enforced "by faulting exceptions and by physical memory encryption." However — this is an important nuance — memory encryption is implementation-defined, not architecturally mandated by the CCA specification. A compliant CCA implementation can exist without inline DRAM encryption, relying solely on GPT/GPC for isolation.

This contrasts with AMD SEV-SNP, where per-VM AES-128 encryption is a core architectural feature, not optional. For deployments where physical DRAM probing is in the threat model, the presence or absence of inline memory encryption is an important platform selection criterion, not something guaranteed by the CCA logo.
